# 开发手记

> 这是一份"实现过程记录"，不是给使用者看的说明书。里面记着：与设计文档的偏差、真环境踩出来的坑、
> 以及一段真实运行的实测数据。上手请看根目录的 [README](../README.md)，参数见 [设置说明](设置说明.md)。

按《聊天机器人平台开发文档 v1.2》实现的 Windows 桌面机器人：
底层调 DeepSeek 官方 API，前端接 QQ 官方机器人，核心是把**前缀缓存**当成一等公民来设计。

- 语言 / 运行时：**C# / .NET 10**（WinForms 托盘 + ASP.NET Core 内嵌配置页）
- 数据：SQLite（WAL + FTS5），单文件库，绿色便携
- 交付形态：**单个 exe**，双击即用，不需要装任何运行时

## 1. 快速开始

> **设置怎么调**：见 [设置说明.md](设置说明.md)（参数表由代码生成，`Bot.App.exe --dump-params <路径>` 可重新导出）。

> 已配置好真实凭据（AppID / AppSecret / DeepSeek Key），直接双击 `publish\Bot.App.exe` 即可。
> 启动后托盘出现图标、浏览器自动打开配置页；`data\settings.json` 里存着明文密钥，
> 分享这个文件夹之前记得先删掉它。

### 直接跑发布版

```
publish\Bot.App.exe
```

双击后：托盘出现图标 → 自动打开 `http://127.0.0.1:8765` 配置页。
关掉网页不影响机器人，右键托盘图标退出。

首次运行会自动生成：

```
Bot.App.exe
data\
  ├─ settings.json    ← 配置（也可以只在网页里改）
  ├─ bot.db           ← 全部数据；拷走整个文件夹 = 搬走机器人
  └─ logs\bot-*.log   ← 按天切分，保留 14 天
```

### 从源码跑

```powershell
cd chatbot
dotnet build ChatBot.slnx
dotnet run --project src/Bot.App          # 托盘模式
dotnet run --project src/Bot.App -- --headless   # 无界面模式（服务器 / 调试）
```

### 发布单文件

```powershell
dotnet publish src/Bot.App -c Release -r win-x64 --self-contained true `
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:EnableCompressionInSingleFile=true -o publish
```

### 没有 API Key 也能验全链路

```powershell
python tools/fake_llm.py 9999          # 本地假模型，会返回合法的总结行
# 配置页里把 Base URL 改成 http://127.0.0.1:9999，API Key 随便填
# 然后到「本地试聊」发消息，轮换/入库/回滚都能验
```

## 4. 与文档的差异（都是实现时才发现的坑）

| 差异 | 原因 |
| --- | --- |
| **新增 `session_turn` 表** | 文档要求崩溃后"补总结"，但会话历史只存在内存里，重启就没了。必须持久化回合。 |
| **新增 `person_open_id` 表** | QQ 群里给的是 `member_openid`，同一人在不同群可能不同。要满足 3.4.8"同一人跨群映射一致"，只能靠 `union_openid` 聚合 + 登记所有见过的 open_id。 |
| **`person.union_open_id` / `chat.kind` / `event.location_label`** | 前两个是平台事实；第三个是因为 `location` 被用作"按群隔离"的作用域键（chat_id），而 chat_id 是不透明串，**绝不能进 prompt**，所以另存一个展示名。 |
| **`message` / `chat_state` / `name_evidence` / `schema_meta` 表** | 文档提到了 `message_buffer` 和名字学习次数，但没给 DDL。 |
| **"上轮摘要"本地生成（60 字）** | 文档 3.3.4 要求它，但 4.4 的总结模板里没有这个字段。再发一次请求不划算，改成从最后两轮对话本地压一句，零成本。 |
| **`reply_length` 写进规则，标记破坏缓存** | 调参要求规则里显示具体字数。既然写进前缀，就必须把 `reply_length` 标成破坏缓存，改动后轮换重建；否则会出现"前缀写 40 字、尾部写 20 字"的冲突。 |
| **被触发时回填「背景」** | 文档说"未触发只记录、不调用 API"，但这样机器人被叫到时看不到前文（`@你 你觉得呢` 里的"呢"指什么它不知道）。现在维护一个"自上次回复以来的群聊"缓冲，触发时把最近 `backfill_max_msgs`（默认 12）条补进尾部的【背景】块。放在尾部不破坏前缀缓存，且只在被触发时才付钱。 |
| **会话中"旁听"并入对话** | 会话一旦开起来，之后收到的群聊不再区分"触发/没触发"，全部作为 `TurnKind.Ambient` 并进历史（`capture_ambient`）。这样它回完一句之后一直在听，下一轮能看到中间所有发言。旁听**不计轮次**，否则话多的群几分钟就把 `session_max_turns` 撑满、频繁轮换。 |
| **会话激活后的"主动接话"节拍** | `active_tick_sec`（默认 120，0=关闭）。会话被触发激活后，每隔 N 秒把这段时间的**所有**群聊汇总成一批、调一次模型并回复，直到 `session_timeout_min` 静默轮换。这才是全量模式该有的"跟随对话"，而不是等下一次被叫。与 `capture_ambient` 互斥（开节拍时旁听会让节拍没素材）。 |
| **疑问句概率独立** | 文档把"疑问句启发式"和"关键词触发"共用 `reply_probability`，实际是两个完全不同的旋钮：前者是"没人问它它也插嘴"，后者是"用户明确提了话题"。现在拆成 `reply_probability`（关键词）和 `question_reply_probability`（疑问句），可以单独关掉其中一个。 |
| **入库按操作独立事务** | 文档说"整批一个事务"，又说"部分成功优于全丢"。两者冲突，取后者 + `batch_id` 记账（仍可一键回滚）。 |
| **检索要求 kw 或 person 至少命中一项** | 纯按文档公式，地点分（权重 2）单独就超过阈值 0.35，等于**同群所有历史事件每轮全量注入**。地点只能当加权项。 |
| **未登录的查询词元不参与分母** | 否则"末吃""锅吗"这类不存在的 bigram 会拿到最高 idf，把真正的命中稀释掉。 |
| **QQ 出站用 chunked → 改成显式 Content-Length** | `JsonContent` 默认 chunked，部分网关不认。 |

## 7. 实测记录（2026-10-28，真凭据）

| 项 | 结果 |
| --- | --- |
| DeepSeek 连通 | `POST /chat/completions` 200，`deepseek-flash`，`thinking=disabled` 时 **596ms** 返回"在的" |
| 该 Key 可用模型 | `deepseek-flash`、`deepseek-v4-pro`（`/models` 只列这两个） |
| QQ 换票 | `POST bots.qq.com/app/getAppAccessToken` → access_token 78 字符，有效期 ~6370s |
| QQ 网关 | `wss://api.sgroup.qq.com/websocket` → READY，`session=87518ac4-…` |
| 单文件 exe | 59.8 MB，headless 与正常模式均能起服务 |

### 只有真凭据才暴露的两个坑（都已修）

1. **`expires_in` 是字符串** `"7200"`，不是数字。映射成 `int` 直接 `JsonException`，
   外层只会看到"网关连接异常"来回重连。已改成先看 `JsonValueKind` 再解析。
2. **`deepseek-flash` 是思考模型**：响应里带 `reasoning_content`，`completion_tokens` 含推理开销。
   同样一句话，"在的"两个字：
   - 开启思考：`prompt 36 / completion 8`（还因为 `max_tokens=8` 被推理吃光，`content` 为空）
   - 关闭思考：`prompt 10 / completion 2`

   所以新增了 `thinking` 参数并**默认 `disabled`**——否则文档 6.1 的 `O = 30–80` 输出成本假设直接失真，
   而且小 `max_tokens` 会稳定返回空回复（`E_EMPTY`）。
   `deepseek-v4-pro` 的推理开销更夸张：两个字要 37 个推理 token。

### 另外发现并修掉的

- **启动阻塞**：重启时要给孤儿会话"补总结"，原来是同步等待模型；API 一慢，托盘和配置页就起不来。改成后台任务。
- **WS 握手无超时**：网络不通时会静默挂很久，加了 20s 上限和全过程日志。
- **网关日志丢失**：`QqGateway` 构造时没传 logger，异常全被 `NullLogger` 吞掉，排查时一片空白。
- **单文件 exe 的 chunked 请求**：`JsonContent` 默认走 chunked，已改成显式 Content-Length。

## 9. 已知限制

- **群消息接收范围取决于群设置**（这一条我写错过两次，现按官方文档更正，见
  [群消息（全量模式）](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html)）：
  - 默认：只收到 @ 机器人的消息，事件 `GROUP_AT_MESSAGE_CREATE`
  - 群主开启「允许机器人接收群内所有消息」后：群里**每一条**消息都推 `GROUP_MESSAGE_CREATE`，
    **Intent 仍然是 1<<25**，不需要额外订阅位
  - 两个事件的差别全在 content 的写法上：全量模式下 @ 某人会变成 `<@该成员member_openid>`，
    被 @ 的人列在 `mentions` 数组里，每个元素带 `bot` 布尔字段
  - 所以判断"有没有 @ 我"必须看 `mentions` 里是否有 `bot=true`；
    **不能**在 content 里找 `<qqbot-at-user>`（那是另一套标签，全量模式不发）。
    content 里的 `<@openid>` 会被还原成 `@昵称` 再进历史，避免 open_id 泄漏进 prompt
  - 收到 `GROUP_MESSAGE_CREATE` 本身就证明群主开了全量，程序会**自动**打开"能旁听全群"能力位
    （关键词触发 / 疑问句触发随之生效）；不再提供手动开关，按群自动识别并显示在当前会话的「接收」列
  - 若开启后一条事件都收不到，多半是开放平台后台还没给该机器人开「群消息接收」权限。
    日志里每条 dispatch 的类型都会打出来，据此判断是"没收到"还是"收到但不认识"
- **`author.username` 有昵称**。文档 3.4.8 的整个前提是"接口不下发昵称"，实测这个字段存在
  （`GROUP_MESSAGE_CREATE` 的 author 带 `username` 与 `member_role`）。目前只写入
  `IncomingMessage.SenderName`，尚未替换「群友NN」标签。
- **纯图片 / 语音 / 卡片 / 合并转发消息直接丢弃**，不进对话、不进未读缓冲、不触发回复
  （日志里记一行「收到无文本消息，已忽略」）。带文字的消息只保留文字部分。
  文档 0.2 明确不做多模态，所以宁可当作没看见，也不要让模型去猜"对方发了张图"。
- 群消息有频率限制，气泡切分（1–3 条）会放大占用；被限流时看日志里的 429。
- 单实例：同时只能跑一个。
- 切换适配器（mock ↔ qq）需要重启；其余设置热生效。
- **单文件 exe 首次启动会把原生库解压到 `%TEMP%`**。极少数把 `%TEMP%` 锁死的环境（例如某些企业管控策略或受限令牌）
  会启动失败，此时设置环境变量 `DOTNET_BUNDLE_EXTRACT_BASE_DIR` 指向一个可写目录即可。

## 10. 编号与容量（跑久了才会遇到的问题）
**E999 之后不会出问题，但另外两处会。**

1. **`E999 → E1000` 是安全的**。编号只补零（`D3`）、不截断，宽度自然增长；
   全项目**没有任何地方把 `E003` 反解析回 id**——`PIN` 指令直接读数字字段，
   且现在同时接受 `E003` 和 `3` 两种写法。编号变宽也不影响前缀哈希：前缀只在轮换时重建，
   会话内的事件集合是冻结的。

2. **真正会撞号的是"群友NN"**。原来取 `person_id` 后两位，第 101 个人会和第 1 个人**同时叫「群友01」**：
   模型会把两个人当成同一个，`ResolveByLabel` 也会随机挑中一个。
   已改成：100 人以内沿用"群友07"，到第 100 个人起改用全编号"群友107"。

3. **活跃事件检索上限**。原来按 `event_id` **正序**取 2000 条，意味着第 2001 条之后的新事件
   永远不参与检索——而新事件恰恰最该被检索到。已改成倒序取 5000 条，命中上限时丢最旧的，
   并在日志里告警。

对应 5 条回归测试见 `tests/Bot.Tests/IdGrowthTests.cs`。

| 指标 | 实测值 | 文档目标 |

| 请求数 | 286（257 chat + 29 summary） | — |
| prompt token | 569,697，其中 **503,296 命中缓存** | — |
| **整体缓存命中率** | **89.3%** | 前缀区 ≥ 90% |
| 总结格式违规 | **0 / 29** | ≤ 5% |
| 发送确认 | 257 / 257（chat） | 幂等发送 |

> 命中率高于文档预期：因为历史区是 append-only 的，官方缓存把**整段 prompt**（不只是前缀）都命中了，
> 稳态下 miss 只剩新增的一小段（约 50–250 token）。

### 真环境才暴露的问题（已修）

1. **群 open_id 进了 prompt**（我引入的 bug）。QQ 不下发群名，代码用 `chat_id` 兜底当群名，
   而 QQ 群的 `chat_id` 就是 32 位 open_id → `【当前】群「7CFF2FD2…」` 每轮都发一遍，
   模型还把它写进了事件记忆。已修：无群名时显示「本群」；事件入库时把不透明串归一成「本群」；
   prompt 组装再加一道 `<id>` 兜底替换（确定性替换，不破坏哈希）；并补了回归测试。
   历史脏数据用 `tools/fix_event_labels.py` 就地修复（修复前已备份 `bot.db.bak-*`）。

### 仍然存在的偏差

- `person` 记忆是**全局**的（`chat_scope` 恒为空），同一个人的记忆会跨群合并；
  文档默认 `memory_scope = per_chat`。事件记忆已经是按群隔离的（`location` = chat_id）。
- 群里的表情以 `<faceType=…>` 下发，现在归一成 `[表情]`（早期版本会原样进 prompt）。
- 贬损词表只覆盖「傻屌/傻逼/废物」这类，"野狗"这种外围词拦截不到——
  群里已经有人在尝试「把某人记成野狗」这种社交攻击，目前靠模型不配合而非程序拦截。
