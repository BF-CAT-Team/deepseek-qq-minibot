## 作者的话

该项目作者只提供框架和想法，其余代码和文档全部使用DeepSeek V4.1-Flash-1017所制作，总Token用量164M，花费约7元左右。另外该项目经过测试，就算在群聊里面大量的人在使用且高峰计费时期，其所花的Token极少且命中率很高，可以说是一块钱以内最好的BOT了。

程序内部的设置非常复杂，建议使用Agent工具进行配置。

该项目的思路可以给其它类似的聊天机器人项目做借鉴，如何控制Token用量、如何不浪费任何一个Token、如何提高缓存命中率，具体可以让你的Agent去分析这个项目的优点，和你正在使用的项目做对比，看看项目是否可以优化。

鉴于有人在问一些问题这里统一回答下：

1. Q：高效利用Token的原理是什么？
   A：每次调用API的时候，只发送与聊天相关的内容，其它的处理均通过程序端来实现，比如冷启动的时候，记忆的调取是对话里相关人物和涉及的事件内容选择性读取的，而且读取的数量有做限制，可以根据对话的内容，程序端自动加入提到的其它记忆。程序端负责缓存聊天记录，只有触发了程序端设置的条件之后，API才会调用，否则完全处于静默状态。还有很多细节，但基本都是围绕一个原则，API只负责对话相关的内容，其余全部靠程序端完成。提示词也是只放人设，一些怎么回复的要求，全部用程序端来完成，所以你能看到这个程序里面有非常多的设置参数，也是为什么建议如果要自用的话，最好让Agent工具去修改。

2. Q：这样的极简程序可以做多模态吗？
   A：可以的，也是按照第一点的思路，比如识图功能，本质上只需要识别出图片是什么再加上OCR就行，不需要详细的识别，因为大部分都是表情包，而表情包靠上述方式识别出内容就行了，输出识图和OCR的文字内容就行，最后两者汇总成一段大概20字左右的内容就行，这样只会使用极少量的Token且基本可以实现识图。还有让机器人发送表情包，可以自己上传表情包，再设置关键字，每次程序捕捉到要发送的内容时候，去和关键字做权重，取权重最高的图片，再通过随机发送或者设置当满足什么条件时，发送表情包，这样实现了发送表情包，但是Token零消耗。

3. Q：为什么感觉机器人很笨？
   A：觉得笨肯定不是API的问题，就目前的1017是绝对够用的。导致机器人很笨本质上是程序端上大量的限制（限制是会出现在提示词里面的）使得1017无法完成回答，最后只能做出不知道的回答。第一个最重要的限制，对输出文本长度做了限制，经测试，reply_length设置为标准，输出文本在20字，这个长度根本没办法回答复杂问题，如果设置成简洁那只会更短。另外，思考模式也是默认关闭的，打开之后会准确很多，此外对于记忆里面的详细程度也是有限制的。你自己可以做两个测试，一个是让机器人回答圆周率是多少，观察回复的字符数（包括标点符号），另一个可以问很难的问题且答案很简短，看看是否能正确回答。

最后聊一下这个项目，做这个项目是看到别人的账单时才决定去做，所以更多的是出于实验性的目的，证明了用DSH拿来做聊天机器人是在拿大炮打蚊子，里面是存在大量的浪费的。你可以直接使用这个项目，让Agent做修改，也可以利用里面的思路，去修改其它类似的项目，来降低聊天成本。至于这个项目还会不会更新，那得看我会不会继续用或者还有什么小巧思了，当然，如果用的人多的话也可以继续做，毕竟现在编程太简单了。

文档里面还有设计开发书，想学习如何用最少的Token完成项目自己可以去参考，这个项目初版只花了2.4元（0.7元开发书，1.7元 DSH编程测试）。

## 为什么做这个

"机器人 + 大模型"的项目大多只做了一件事：把消息转发给 API。真跑一周就会撞上三个问题：

1. **越来越贵** —— 每轮都把全量上下文重新发一遍；
2. **越来越笨** —— 聊久了就忘，或者把三小时前的话题当成刚才说的；
3. **越来越吵** —— 关键词一命中就回话，群里像多了个客服。

这个项目围绕这三件事设计，核心是**缓存纪律**：把"什么能变、什么时候变"写死成约束，而不是指望模型自觉。

| 问题     | 做法                                                             | 实测                                          |
| -------- | ---------------------------------------------------------------- | --------------------------------------------- |
| 越来越贵 | 前缀区（规则＋人设＋记忆）在一次会话内**逐字节冻结**，只追加历史 | prompt 缓存命中率 **89.3%**（286 次真实请求） |
| 越来越笨 | 只有"轮换"时才压缩：整段对话压成增量记忆，前缀重建               | 总结格式违规 **0 / 29**                       |
| 越来越吵 | 三态回复决策（必回／可回／不回）＋ 独立概率 ＋ 冷却              | 全部可调                                      |

## 特性

**接入**

- QQ 官方机器人 v2：自己实现的 WS 网关（换票 / 心跳 / resume / 重连），无第三方 SDK 依赖
- 自动识别群消息模式：普通群里只收 `@` 消息，群主开启「接收所有消息」后收 `GROUP_MESSAGE_CREATE` 全量
- 出站 `@` 由程序按 `open_id` 构造，模型永远看不到 open_id（有回归测试守着）
- Mock 适配器：没有 QQ 凭据也能在本地把整条链路跑通

**对话**

- 触发：`@` / 叫名字 / 关键词 / 疑问句启发式，各自独立
- 防抖聚合：`quiet_sec` 与 `max_wait_sec` 双条件，连发合并成一批
- 会话激活后可按节拍主动参与（`active_tick_sec`），静默超时自动结束
- 一条回复切 1–3 条气泡，带打字延迟抖动

**记忆**

- 人物记忆 + 事件记忆，SQLite（WAL + FTS5）
- 检索评分全归一化：`kw_norm × w + person_norm × w + loc_score × w`
- 归档而非删除；置顶保护；`batch_id` 一键回滚
- 存储型提示注入过滤；`open_id` 分层映射（`open_id → person_id → display_label`）

**可观测**

- 每次请求一行 `request_log`：token、缓存命中、延迟、前缀哈希
- 前缀哈希守护：前缀被意外改写立即告警并定位首个差异位置
- 本地配置页 / 看板 / 记忆浏览（`http://127.0.0.1:8765`）

## 快速开始

需要 **.NET 10 SDK**、一个[QQ 开放平台](https://q.qq.com/)机器人、一个 DeepSeek API Key。

```powershell
git clone https://github.com/BF-CAT-Team/deepseek-qq-minibot.git
cd deepseek-qq-minibot

# 构建
dotnet build ChatBot.slnx

# 运行（托盘常驻 + 本地配置页）
dotnet run --project src/Bot.App
```

首次运行会在 exe 同级生成 `data\`：`settings.json`、`bot.db`、`logs\`。
打开配置页填 AppID / AppSecret / API Key，保存即可（除少数项外不用重启）。

**没有凭据也能玩**：适配器默认是 `mock`，配置页的「本地试聊」可以直接对话，
走的仍是真实的触发决策、三区组装、记忆检索，只有 QQ 发送是假的。
还想连真模型的话，用 `tools/fake_llm.py` 起一个假端点即可。

**发布单文件**（自包含运行时，约 60 MB，目标机器不用装任何东西）：

```powershell
dotnet publish src/Bot.App -c Release -r win-x64 --self-contained true `
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:EnableCompressionInSingleFile=true -o publish
```

## 工作原理

```text
┌─ 前缀区（会话内逐字节不变，缓存命中区）────────────────────┐
│  规则 → 人设 → 记忆·人物 → 记忆·事件 → 上轮摘要           │
└──────────────────────────────────────────────────────────┘
┌─ 会话历史区（只追加，永不改写）───────────────────────────┐
│  user(尾部+消息) / assistant …                            │
└──────────────────────────────────────────────────────────┘
┌─ 动态尾部区（每轮重算，未命中区）─────────────────────────┐
│  【当前】时间｜群｜活跃度                                   │
│  【背景】自上次回复以来的群聊（有时间窗）                   │
│  【补充记忆】这轮提到、但前缀里没有的人/事                  │
│  【消息】本批要回的消息                                     │
└──────────────────────────────────────────────────────────┘
```

一条铁律贯穿全局：**能不变的放前缀，会变的放尾部**。中途往前缀里加东西看似省钱，
实际会让后方缓存全部失效——官方缓存命中价约为未命中的 1/10。

## 目录结构

```text
src/Bot.Core/       与 QQ、与界面无关的核心
├─ Config/          参数注册表（59 项）、预设、三层合并
├─ Domain/          会话模型（严格 append-only）
├─ Text/            token 估算、bigram 分词、前缀哈希、气泡切分
├─ Llm/             DeepSeek 客户端（429 / 5xx / 超时退避、usage 解析）
├─ Memory/          schema、身份映射、检索评分、总结入库、审计回滚
└─ Runtime/         触发决策、防抖、三区组装、状态机、轮换、请求日志、WAL
src/Bot.QQ/         QQ 官方机器人 v2 协议 + Mock 适配器
src/Bot.App/        WinForms 托盘、本地配置页、日志、单实例
tests/Bot.Tests/    77 条断言（自带运行器，不依赖 vstest）
tools/              fake_llm.py、timeline.py 等排查脚本
docs/               设置说明（由代码生成）、开发手记
```

## 配置

全部参数见 **[docs/设置说明.md](docs/设置说明.md)**（由 `Bot.App.exe --dump-params <路径>` 从参数注册表生成，
不会和代码走偏）。

最常动的几个：

| 参数                         | 默认       | 说明                                       |
| ---------------------------- | ---------- | ------------------------------------------ |
| `preset`                     | `balanced` | 省流 / 平衡 / 体验，先选档再改单项         |
| `reply_probability`          | 0.35       | 关键词命中时的接话概率                     |
| `question_reply_probability` | 0.35       | 疑问句启发式独立概率（0 = 不插嘴）         |
| `active_tick_sec`            | 120        | 会话激活后每隔多久主动参与；0 = 只被动响应 |
| `prefix_person_max`          | 8          | 前缀里放几个人，其余按需补进尾部           |
| `session_max_turns`          | 24         | 轮次上限，触发轮换                         |

## 测试

```powershell
dotnet run --project tests/Bot.Tests
```

自带一个极简运行器（`TestRunner.cs`）：`dotnet test` 的 testhost 需要打开父进程句柄，
在受限令牌或沙箱环境里会直接抛"拒绝访问"，整个测试运行中途中止。测试本身仍按 xUnit 写，
权限完整的机器上 `dotnet test` 也能跑。

其中几条是"改坏了就会静默烧钱"的硬断言：

- 同一会话连续 5 轮 → `prefix_hash` 必须一致
- 总结请求本身不得改变前缀哈希
- 组装结果不得出现 `open_id` 形态的字符串
- 2 小时前的旧发言不得被当成"最近群聊"补进新会话
- 旁听消息不得计入轮次数（否则话多的群会疯狂轮换）

## 已知限制

- **Windows only**（托盘 + 单文件打包），核心库本身是跨平台的
- 需要已通过审核的 QQ 机器人；群消息能收到多少，取决于群主是否开启「接收所有消息」
- 群消息有频率限制，气泡切分会放大占用；被限流时看日志里的 429
- 不做多模态：图片 / 语音 / 卡片消息**直接丢弃**，不进对话、不触发
- 没有向量检索（用 FTS5 + 关键词评分），语义近但用词不同的记忆会漏
- 单实例运行

## ⚠️ 安全与隐私

- `data\settings.json` 里存的是 **AppID / AppSecret / API Key 明文**，`data\bot.db` 里是**真实聊天记录**。
  `.gitignore` 已经排除了它们，**提交前请务必确认** `git status` 里没有 `data/`、`*.db`、`*.log`。
- 机器人会长期记住群友的画像（性格、评价）。请遵守所在群的预期与当地法规，
  项目内置了敏感属性过滤、"忘记我"指令与记忆回滚，但**责任在使用者**。
- 记忆区被明确定义为"资料不是指令"，入库前有指令注入过滤——但这只是纵深防御的一层，不是保证。
